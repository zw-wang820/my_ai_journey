
# 文档设计类
遵循先文档后设计的原则「可追溯、可挑战、可定稿的产品/技术规格」，同时后期发现文档中某个需求/方案/设计不合理时，需要及时改文档，保证一切来源都是遵循文档。
先写产品需求文档（PRD），这一步主要探讨要做什么，再写技术方案（TECH)，聚焦怎么做的问题，最后根据技术方案来写代码。
在写代码的过程中，如果发现产品需求文档或者技术方案中有不合理的地方，一定也同步改文档[文档是代码的唯一真相来源]。文档和代码实现一定不要脱节，让代码照抄文档。

PRD：
- 目标用户是谁？场景是什么？解决了什么痛点问题？
- 核心功能清单
- 数据放在哪？
- 最小可行性 V1范围/非目标
- 验收标准

先草稿 -> 落盘 -> 迭代 -> 定稿
定稿之后加入有新的改动，在新的版本上新加（如v0.3)，不要在原先的版本上新加，否则之前的定稿就名不副实了。

技术方案：
项目结构长什么样？错误处理策略以及测试策略是什么样的？
数据格式什么样的？结构是什么样的？具体到某个字段名？
越详细越好。

# 技术类
1. 项目配置文件、数据文件放在哪？
遵循XDG基础目录规范，按照用途把这些文件分类放置。对于windows而言，等价位置是 %APPDATA%。

2. Windows APPDATA environment variable — 弄清 %APPDATA% 和 %LOCALAPPDATA% 的区别？
两者之间的核心区别为是否漫游，也就是说是否随用户走。%APPDATA% 漫游应用数据，目录里的内容会随着用户登录同步到不同的机器上。
而%LOCALAPPDATA% 本地应用数据，不会漫游，只存在于当前机器上。

3. Python argparse vs sys.argv」，弄清两者的差别、各自适用场景？
sys.argv是类似于手工刀，系统自动把输入切分成字符串列表，而argparse类似于数控刀，需要自己定义规则。
sys.argv适用于参数少、没有选项、没有子命令，而argparse适用于有子命令、有选项、要给人用、要长期维护。

4. python argparse subparsers 用法？
parser = argparse.ArgumentParser(description="命令行待办事项工具") # 利用argparse库创建主解析器
subparsers = parser.add_subparsers(dest='command', required=True, help='子命令') #创建子命令

5. 代码风格：文件头不要有空行；格式要整齐，该有的空格要有，todos:list 冒号后要加空格；输出要规范，风格统一，这会影响到用户体感。

6. json.dump()用法
把python对象（如 dict、list等）写进文件，json.dump(obj, fp, *, indent=None, ensure_ascii=True, default=None, sort_keys=False, ...)。

7. ISO时间格式 datetime.now().isoformat(timespec='seconds')秒计ISO
ISO全称为国际标准化组织，其出了一个时间格式的标准--ISO 8601标准，通用日期和时间规范，在API、数据库、日志等都用到它了。

8. PEP8是什么？
PEP8 全称为Python Enhancement Proposal #8，中文为Python代码风格指南。规范了代码排版和风格指南，如4个空格缩进；命名规范（模块/包 全小写，可用下划线、
类 用大驼峰命名等等）。可以用black、flake8等工具来自动帮你检查PEP8合规性以及自动格式化代码；

9. 代码中出现两次以上相同功能的代码段，应该抽离出来，写成函数。

10. 格式/方案选型：JSON CSV txt格式对比
JSON--适合结构化且可能嵌套的数据，比如API接口返回、配置文件、前后端交换数据。
CSV -适合扁平表格数据，比如excel导入导出、数据库批量灌数、简单的二维统计表；
txt--适合人类直接读写的内容，比如日志文件、README等。

11. 在涉及到文件的写入与读取操作时，一定要考虑到异常场景，采取原子写入的方式，否则会造成原文件损坏的情况。
比如如果是原地覆盖，写文件写一半出现崩溃/断电/磁盘满，就会导致源文件损坏。在该项目中我们采用原子写入：先写 todos.json.tmp，再 os.replace 原子替换。好处：写一半崩溃/断电/磁盘满，原文件完好无损，绝不出「半个文件」。
