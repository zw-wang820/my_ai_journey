## 四、踩过的坑（关键教训）

1. **文档与代码脱节**（M1）——代码自创字段名 `text/Done/created`，与 TECH 定稿的 `content/done/created_at` 不一致。教训：**文档是代码的唯一真相来源**，写代码时发现文档字段名不合适 → 先改文档，再改代码。
2. **直接覆盖文件 vs 原子写入**（M1）——直接 `open(TODO_FILE,'w')` 会在写一半崩溃时毁掉数据。教训：**先写 `.tmp` 再 `os.replace`**，保证「要么完整成功，要么原样不动」。
3. **save 放在 if 外导致数据销毁**（M2）——找不到 todo 时仍执行 `save_todos`，会把空列表写回文件、覆盖损坏的原始数据。教训：**save 只在数据真的变化时才执行**。
4. **`len+1` 生成 id 的隐患**（M1）——删除中间项后会重复 id。教训：用 **`max(id, default=0)+1`**。
5. **`''.join` vs `' '.join`**（M3）——空字符串拼接会悄悄删掉用户输入的空格，破坏数据保真。教训：**忠实用户输入**；「我觉得这样更好」是初学者最危险的念头，先确认正确再考虑优雅。
6. **时间格式脱节**（M1）——`isoformat()` 默认带 6 位微秒，与 TECH 秒级示例不一致。教训：`isoformat(timespec='seconds')`。
7. **`exit` 命令冗余**（M2）——「一次一命令」模式下进程执行完自动退出。教训：**实现时发现需求不合理 → 回去改文档**，不硬实现没用功能。
8. **测试脚手架泄漏**（M4）——AC-9 测完忘删 `time.sleep(3)`，导致每条命令卡 3 秒。教训：**测试脚手架用完必删**，是收官前的最后一道门禁。

## 五、学到的工程纪律

| 纪律       | 一句话                                           |
| -------- | --------------------------------------------- |
| 先文档后代码   | PRD（要什么）→ TECH（怎么做）→ 代码（照着做）                  |
| 对比后选型    | JSON vs CSV vs 文本、argparse vs sys.argv，都先对比再定 |
| 命名用英文术语  | 不用拼音（`biaoji` → `done`），snake_case            |
| 出现两次就抽函数 | `find_todo_by_id` 三命令复用                       |
| 输出规范统一   | 编号 `#N`、中文冒号 `：`、`->` 仅表变化                    |
| 数据安全优先   | 原子写入 + save 条件执行 + 损坏不覆盖                      |
| 忠实用户输入   | 不擅自改写（空格、微秒、字段名都对齐文档）                         |
