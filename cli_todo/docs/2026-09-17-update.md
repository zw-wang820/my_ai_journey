## 三、commit ② feat：存储层错误输出改用 logging

### 改动范围
| 文件 | 位置 | 改动 |
|---|---|---|
| `models/storage.py` | `load_todos()` 文件不存在分支 | 「已初始化待办列表」**保留 `print`** |
| `models/storage.py` | `load_todos()` `except JSONDecodeError` | `print` → `logging.error("错误：%s 内容损坏，请检查后重启", TODO_FILE)` |
| `models/storage.py` | `save_todos()` `except OSError` | `print` → `logging.error("保存失败：%s", e)` |
| `models/storage.py` | `load_todos` docstring | 修掉尾部多余空行 |
| `main.py` | `if __name__ == "__main__"` 块首 | 新增 `logging.basicConfig(level=logging.WARNING, format="%(levelname)s: %(message)s")` |
| `main.py` | 模块头部 | 补充模块 docstring |

### 根因
- `print` 是「单向广播」：没有级别、没有时间、没有来源，无法被过滤、无法被归档、无法被重定向。
  一旦要区分「给用户看的」和「给开发者看的」，就必须有级别——这就是 `logging` 存在的理由。
- **分流原则**：纯用户提示（初始化成功）留 `print`；用户和开发者都需要的信息（数据损坏、写入失败）走 `logging.error`。
- **`basicConfig` 放在 `if __name__` 块内**：若放模块顶层，任何 `import`（包括 pytest 收集测试）都会执行它、
  污染全局日志配置。放在入口块内，只有真正当 CLI 跑时才生效。
- **惰性 `%s` 而非 f-string**：`logging.error("保存失败：%s", e)` 把格式化推迟到「这条日志确定要输出」的那一刻；
  f-string 则无论级别是否放行都会先拼字符串，白做功，且让日志系统拿不到原始模板、无法聚类。

## 五、真机复验点

用临时 `APPDATA` 隔离数据目录，避免污染真实数据：

| 场景 | 操作 | 预期 |
|---|---|---|
| A 首次运行 | 指向一个空的 `%APPDATA%\cli_todo`，执行 `python main.py list` | stdout `已初始化待办列表` + `暂无待办事项`，退出码 0 |
| B 文件损坏 | 把 `todos.json` 写成一段非法 JSON，执行 `python main.py list` | stderr `ERROR: 错误：<path> 内容损坏，请检查后重启`，退出码 2 |

复验要确认两点：① 控制台能看到 `ERROR:` 前缀（说明 `basicConfig` 的 format 生效）；
② 用户照样看得懂这条报错（说明改用 logging 没有把信息藏起来）。
